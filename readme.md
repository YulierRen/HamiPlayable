# Hami Playable 方案设计

## 1. 工程解决方案设计

### 1.1 项目目标

在规定周期内交付可玩的 Playable 成品。

### 1.2 业务拆解与职责分配

围绕“设计稿到可运行”的完整链路，在写代码之前，逻辑上拆成 5 个业务模块：

1. 设计资产落地模块

- 输入：Figma JSON、切图资源。
- 输出：可直接在 Cocos 使用的节点与资源映射。
- 价值：减少手工摆放误差，降低后续改版成本。

2. 核心玩法模块

- 输入：initial（初始的宝石的状态）、slot/tray（放宝石的板子）、base（正确的宝石位置） 的交互规则。
- 输出：稳定可玩的主流程（选中、挪入、搬运、排序）。
- 价值：保证“可玩性”先成立。

3. 体验表现模块

- 输入：交互动效要求（浮起、回落、落地反馈）。
- 输出：玩家可感知的反馈节奏。
- 价值：提升完成度与留存。

4. 引导与留存模块（没做，文档中没要求）

- 输入：新手路径与关键行为节点。
- 输出：可执行的新手引导和触摸限制策略。
- 价值：降低首轮流失。

5. 商业化接入模块（没做，文档中没要求）

- 输入：平台广告要求。
- 输出：Banner/插屏的统一接入与触发策略。
- 价值：为投放和变现做准备。

### 1.3 关键方案（面向业务目标）

#### 方案 A：Figma 到 Cocos 自动化

做法：

1. 脚本读取 Figma JSON。
2. 统一坐标和尺寸规则，自动转换。
3. 批量创建节点并挂载图片。

业务收益：

1. 上线前改图/改尺寸时可快速重跑，减少返工。
2. 减少人工摆放导致的线上偏差。

#### 方案 B：节点组织方式标准化

做法：

1. 父节点记录逻辑位置。
2. 子节点挂图片并负责视觉变化。

业务收益：

1. 后续改视觉不易影响规则。
2. 设计调整时成本更可控。

#### 方案 C：性能优先的资源策略

做法：

1. slot/tray、base、initial 资源打成统一图集。
2. 降低 DrawCall，避免掉帧。

业务收益：

1. 投放端加载和运行更稳定。
2. 减少因性能问题导致的流失。

#### 方案 D：交互流程稳定化

做法：

1. 统一处理节点移动动画与层级。
2. 批量挪出/排序时按业务时序控制（先挪出，再排序）。

业务收益：

1. 解决视觉上的表现问题，比如宝石在移动过程中被别的图层覆盖。

### 1.4 架构方案

本项目按“总控编排 -> 交互控制 -> 规则服务 -> 地图索引 -> 动画能力”分层。下面按脚本说明：代码怎么设计、输入输出、解决什么问题、原理是什么。

1. 总控层

- gameManager.ts
    - 代码设计：只做模块装配与生命周期管理，不写玩法判断。
    - 输入：场景根节点、mapHelper 提供的节点集合、动画过渡层节点 ani。
    - 输出：可工作的控制器实例与模块间联动关系。
    - 解决问题：避免把初始化、交互、规则混写在一个文件，导致后续改动容易互相影响。
    - 原理说明：
        1. 进入游戏时统一初始化 initial/slot/base 三个控制器，让它们从一开始就使用同一套上下文。
        2. 在这里注入动画过渡层，保证所有跨容器移动走同一条链路，视觉上不会有“有些移动在顶层、有些不在顶层”的不一致。
        3. 销毁阶段统一解绑，避免重复进入场景时事件叠加。

2. 交互控制层

- controller/initialNodeController.ts
    - 代码设计：专注 initial 区域交互，连锁状态本身交给状态服务管理。
    - 输入：点击事件、当前节点、mapHelper 的连通查询能力。
    - 输出：连锁节点列表变化、节点浮起/回落、向目标区域发起搬运。
    - 解决问题：解决“用户点击行为”和“连锁规则计算”耦合导致的难维护问题。
    - 原理说明：
        1. 点击后先做命中与状态切换，再调用连通搜索得到同名连锁集合。
        2. 浮起与回落都基于记录的基准状态执行，保证多次点击后不会越漂越偏。
        3. 对外只暴露当前连锁结果，降低其他模块对 initial 内部细节的依赖。

- controller/slotTrayController.ts
    - 代码设计：专注 slot 的点击交互与视觉反馈，把排序计算委托给 slotArrangementService。
    - 输入：slot 点击事件、当前高亮集合、initial 连锁变化通知。
    - 输出：高亮切换结果、挪入挪出动作、对排序服务的触发。
    - 解决问题：解决 slot 规则频繁变更时控制器越来越臃肿的问题。
    - 原理说明：
        1. 先响应玩家操作（高亮、取消高亮），再触发规则服务，保证操作反馈即时。
        2. 批量挪出时先执行移动，等待动画完成后再统一压缩排序，避免“边飞边重排”的跳动观感。
        3. 通过启停监听控制可交互时机，减少误触导致的重复处理。

- controller/baseController.ts
    - 代码设计：把 base 作为统一落点入口，屏蔽 initial 来源和 slot 来源差异。
    - 输入：base 点击、当前连锁 initial 节点、当前高亮 slot 节点。
    - 输出：可落点搬运结果、base 占用状态更新。
    - 解决问题：解决“两个来源两套落地逻辑”导致口径不一致的问题。
    - 原理说明：
        1. 先确定来源（initial 或 slot），再用同一套可达性和可落点评估。
        2. 搬运成功后统一更新 base 占用态，后续判断直接使用状态，不重复扫描。
        3. 不满足条件时走兜底处理，避免点击后没有反馈。

3. 规则服务层

- services/slotArrangementService.ts
    - 代码设计：纯规则引擎，不直接监听点击；通过依赖注入调用外部移动与映射动作。
    - 输入：待挪入节点、按顺序的 slot 列表、当前占用状态。
    - 输出：目标槽位决策、右移计划、压缩计划。
    - 解决问题：解决排序规则散落在控制器中，改一条规则要改很多地方的问题。
    - 原理说明：
        1. 挪入规则是“同名后插，必要时右移找空位，没空位则失败”。
        2. 挪出后压缩规则是“把后面的非空向前补空”，并支持并行移动与统一收尾。
        3. 同样输入得到同样输出，便于回归测试和问题复现。

- services/baseConnectivityService.ts
    - 代码设计：只负责 base 连通与可落点筛选，不处理动画与点击。
    - 输入：起点 base、候选 base 集合、当前节点名称与占用状态。
    - 输出：可达 base 集合、可用落点集合。
    - 解决问题：解决 base 判断条件复杂、重复判断多的问题。
    - 原理说明：
        1. 先做连通范围判断，再按占用和名称规则筛选可用落点。
        2. 把所有入口都收敛到这套判断，保证规则一致。

- services/initialChainStateService.ts
    - 代码设计：单一状态中心，提供读写和订阅接口。
    - 输入：连锁选中变化、移除变化、清空操作。
    - 输出：最新连锁集合与变化通知。
    - 解决问题：解决多个控制器各自持有连锁状态导致的冲突问题。
    - 原理说明：
        1. 状态只维护一份，任何变化都通过服务通知出去。
        2. 控制器只消费状态，不复制状态，减少不同步风险。

4. 基础能力层

- singleton/mapHelper.ts
    - 代码设计：地图索引和查询统一入口。
    - 输入：场景中的 initial/base/slot 节点结构。
    - 输出：按功能分类的节点集合、同名连通查询结果。
    - 解决问题：解决运行时反复遍历场景查节点导致的效率和稳定性问题。
    - 原理说明：
        1. 启动时先构建索引，运行时直接按索引读。
        2. 连通搜索统一实现，避免每个模块自己写一套查找逻辑。

- animation/nodeAnimationService.ts
    - 代码设计：把位置、缩放、跨父节点移动统一收口，并提供动画完成回调。
    - 输入：移动目标节点、目标容器、目标位置、目标缩放、顺序参数。
    - 输出：一致的移动表现、动画完成信号。
    - 解决问题：解决多个模块各自写 tween 造成时序冲突和视觉不一致的问题。
    - 原理说明：
        1. 跨容器移动先记录世界坐标，再挂到过渡层移动，最后落回目标容器。
        2. 通过完成回调衔接后续业务（例如再排序），保证“动作做完再进入下一步”。

- animation/animationConfig.ts
    - 代码设计：集中参数配置文件。
    - 输入：业务期望节奏（速度、延迟、缓动）。
    - 输出：统一动画参数。
    - 解决问题：解决“调手感要改多处代码”的低效率问题。
    - 原理说明：
        1. 参数集中后，调速和调节奏只改配置。
        2. 与业务逻辑解耦，降低误改玩法逻辑的风险。

## 2. 成品差距与落地路径

### 差距 1：关键反馈不够强（浮起、落地高亮）

玩家视角：

1. 选中和落地的“成功感”不够明显，主要是高亮动画未对齐。
2. 与参考 Playable 相比，完成动作后的确认反馈偏弱。

落地路径：

1. 先上线轻量版高亮（白条扫光 + 短时触发），一周内可落地。
2. 再升级为材质高亮方案，统一控制强度与节奏。
3. 在两个关键节点触发：选中浮起、落地成功。

### 差距 2：slot/tray 视觉尺寸与参考不一致

玩家视角：

1. 宝石从 initial 到 slot 的尺寸变化不明显，和参考的视觉节奏不一致。
2. 玩家容易感知为“只是平移”，而不是“进入槽位并完成状态转换”。

落地路径：

1. 以 slot 目标尺寸作为统一标准。
2. 同步校准吸附范围、浮起高度、缩放比例。
3. 将尺寸参数配置化，便于后续按渠道版本快速微调。

### 差距 3：缺少新手引导

玩家视角：

1. 新玩家理解路径依赖自学，首轮流失风险高。

落地路径：

1. 增加单例引导管理。
2. 增加可点击白名单与遮罩阻断。
3. 按玩家进度逐步放开交互。

### 差距 4：广告能力未上线（Banner/插屏）

玩家与业务视角：

1. 现阶段仅可玩，不可运营。

落地路径：

1. 建立统一广告管理入口。
2. 按平台策略做适配。
3. 插屏设置频控和失败回退，避免打断体验。
