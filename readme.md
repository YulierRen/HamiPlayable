# Hami Playable 方案设计

## 1. 工程解决方案设计

### 1.1 项目目标

在规定周期内交付可玩的 Playable 成品。

### 1.2 业务拆解与职责分配

围绕“设计稿到可运行”的完整链路，在写代码之前，逻辑上拆成 5 个业务模块：

1. 设计资产落地模块

- 输入：Figma JSON、切图资源。
- 输出：可直接在 Cocos 使用的节点与资源映射。
- 价值：减少手工摆放误差，降低后续改版成本。

2. 核心玩法模块

- 输入：initial（初始的宝石的状态）、slot/tray（放宝石的板子）、base（正确的宝石位置） 的交互规则。
- 输出：稳定可玩的主流程（选中、挪入、搬运、排序）。
- 价值：保证“可玩性”先成立。

3. 体验表现模块

- 输入：交互动效要求（浮起、回落、落地反馈）。
- 输出：玩家可感知的反馈节奏。
- 价值：提升完成度与留存。

4. 引导与留存模块（没做，文档中没要求）

- 输入：新手路径与关键行为节点。
- 输出：可执行的新手引导和触摸限制策略。
- 价值：降低首轮流失。

5. 商业化接入模块（没做，文档中没要求）

- 输入：平台广告要求。
- 输出：Banner/插屏的统一接入与触发策略。
- 价值：为投放和变现做准备。

### 1.3 关键方案（面向业务目标）

#### 方案 A：Figma 到 Cocos 自动化

做法：

1. 脚本读取 Figma JSON。
2. 统一坐标和尺寸规则，自动转换。
3. 批量创建节点并挂载图片。

业务收益：

1. 上线前改图/改尺寸时可快速重跑，减少返工。
2. 减少人工摆放导致的线上偏差。

#### 方案 B：节点组织方式标准化

做法：

1. 父节点记录逻辑位置。
2. 子节点挂图片并负责视觉变化。

业务收益：

1. 后续改视觉不易影响规则。
2. 设计调整时成本更可控。

#### 方案 C：性能优先的资源策略

做法：

1. slot/tray、base、initial 资源打成统一图集。
2. 降低 DrawCall，避免掉帧。

业务收益：

1. 投放端加载和运行更稳定。
2. 减少因性能问题导致的流失。

#### 方案 D：交互流程稳定化

做法：

1. 统一处理节点移动动画与层级。
2. 批量挪出/排序时按业务时序控制（先挪出，再排序）。

业务收益：

1. 解决视觉上的表现问题，比如宝石在移动过程中被别的图层覆盖。

### 1.4 架构方案

本项目架构按“总控编排 -> 交互控制 -> 规则服务 -> 地图索引 -> 动画能力”分层。

1. 总控层

- gameManager.ts
    - 业务职责：项目入口，负责初始化和销毁各模块，保证模块之间的交互顺序正确。
    - 重点原理：
        1. 只负责装配，不写具体玩法规则。
        2. 统一注入动画过渡层，保证所有移动过程视觉一致。

2. 交互控制层

- controller/initialNodeController.ts
    - 业务职责：处理 initial 区点击、连锁选中、浮起与回落，以及从 initial 向 slot/base 的搬运触发。
    - 重点原理：
        1. 点击处理与规则计算分离，点击层只做事件和状态切换。
        2. 连锁状态集中管理，避免多处维护导致错乱。

- controller/slotTrayController.ts
    - 业务职责：处理 slot 区点击、高亮、宝石挪入、挪出、空位压缩触发和监听启停。
    - 重点原理：
        1. 先处理交互反馈，再调用规则服务落位。
        2. 批量挪出时支持等待动画完成后统一排序，保证玩家观感连续。

- controller/baseController.ts
    - 业务职责：处理 base 区点击，决定哪些节点可以搬过去，并发起批量搬运。
    - 重点原理：
        1. 入口统一，避免 initial 和 slot 两套逻辑重复。
        2. 搬运成功与失败都可回退到兜底逻辑，保证流程不中断。

3. 规则服务层

- services/slotArrangementService.ts
    - 业务职责：承接 slot 排序规则，包括同名后插、必要右移、无空位失败、挪出后压缩。
    - 重点原理：
        1. 规则集中到单点，改玩法时只改一处。
        2. 输出是确定性的槽位结果，方便做回归测试。

- services/baseConnectivityService.ts
    - 业务职责：负责 base 可达与可落点判断。
    - 重点原理：
        1. 把“能不能放”从控制层剥离，减少复杂 if 嵌套。
        2. 保证规则口径一致，避免边界行为不一致。

- services/initialChainStateService.ts
    - 业务职责：管理连锁节点集合、顺序和变化通知。
    - 重点原理：
        1. 状态单一来源，避免多个控制器各自缓存。
        2. 通过订阅机制同步 UI，减少耦合。

4. 基础能力层

- singleton/mapHelper.ts
    - 业务职责：维护地图索引、容器访问、同名连通搜索。
    - 重点原理：
        1. 用索引换取稳定性和开发效率，减少运行时全场景查找。
        2. 统一坐标和节点查找口径，降低数据不一致风险。

- animation/nodeAnimationService.ts
    - 业务职责：统一移动和缩放动画，管理跨容器移动过程中的层级与过渡。
    - 重点原理：
        1. 先确保业务时序正确，再做动画呈现。
        2. 动画完成回调用于衔接后续业务动作（例如再排序），避免“动画未完逻辑先走”。

- animation/animationConfig.ts
    - 业务职责：集中维护时长、缓动、批量延迟等参数。
    - 重点原理：
        1. 参数集中，便于快速调手感。
        2. 与逻辑解耦，改动效不需要改规则代码。

5. 架构收益（业务视角）

1. 迭代效率更高：规则变更、表现优化、广告接入可并行推进。
1. 风险更可控：每层职责单一，问题定位更快。
1. 交付更稳：即使部分体验模块延后，也不影响核心可玩链路上线。

## 2. 成品差距与落地路径

### 差距 1：关键反馈不够强（浮起、落地高亮）

玩家视角：

1. 选中和落地的“成功感”不够明显，主要是高亮动画未对齐。
2. 与参考 Playable 相比，完成动作后的确认反馈偏弱。

落地路径：

1. 先上线轻量版高亮（白条扫光 + 短时触发），一周内可落地。
2. 再升级为材质高亮方案，统一控制强度与节奏。
3. 在两个关键节点触发：选中浮起、落地成功。

### 差距 2：slot/tray 视觉尺寸与参考不一致

玩家视角：

1. 宝石从 initial 到 slot 的尺寸变化不明显，和参考的视觉节奏不一致。
2. 玩家容易感知为“只是平移”，而不是“进入槽位并完成状态转换”。

落地路径：

1. 以 slot 目标尺寸作为统一标准。
2. 同步校准吸附范围、浮起高度、缩放比例。
3. 将尺寸参数配置化，便于后续按渠道版本快速微调。

### 差距 3：缺少新手引导

玩家视角：

1. 新玩家理解路径依赖自学，首轮流失风险高。

落地路径：

1. 增加单例引导管理。
2. 增加可点击白名单与遮罩阻断。
3. 按玩家进度逐步放开交互。

### 差距 4：广告能力未上线（Banner/插屏）

玩家与业务视角：

1. 现阶段仅可玩，不可运营。

落地路径：

1. 建立统一广告管理入口。
2. 按平台策略做适配。
3. 插屏设置频控和失败回退，避免打断体验。
